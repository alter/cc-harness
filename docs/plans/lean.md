# lean — the test coverage level is chosen at /intake, smallest by default

## Goal
A project chooses how much testing it carries, and the harness stops demanding a test for every change by default. `docs/PROJECT.md` §6 holds one row, `Test coverage level`, with three values: `critical` (the default, and what applies when the row or the file is absent), `standard`, `release`. `/intake` asks for it with `critical` first and the reason in the question text. The contract, the template, `/plan`, `/run-task`, `/run`, `/test`, `/task`, `/verify-task` and the verifier read the row instead of carrying one unconditional rule. `/test` called by hand analyses the code and the existing tests, proposes a list of what to cover and writes only after agreement. Measured on seven projects (labels A–G) before this plan: writing tests took about as long as writing product code in three of them (C 21.8 against 23.4 minutes, E 1.2 against 1.4, G 6.8 against 4.2; project B is left out, its tests are probe scripts and it has no test suite), while, as the reports print them, the step "red first" took at most 1.7% of active time in five of the six projects that measured it and 5.9% in the sixth, and "reverse control" at most 1.1% in all six. So the smallest level removes the obligation to write a test for non-critical code and the coverage ratchet, and keeps both cheap steps for the tests that are written.

## Decisions
- D1 A project without the level row, or without `docs/PROJECT.md` -> `critical` applies everywhere as soon as the harness is installed; `/intake` or `/intake refresh` writes the row, and a mature project gets `standard` or `release` there or by a hand edit.
- D2 Task trees -> in scope. At `critical` the validator stops requiring the reverse-control item and `/task` writes it only for a task with critical code. `/task`, finding an older validator in a project, offers to copy the new one and touches nothing without a yes.
- D3 A fixed bug at `critical` -> always gets the test that would have caught it, in critical code and outside it.
- D4 Acceptance -> reference checks in `selftest.sh` plus one live `agenttest.sh` case; one paid model run is approved.
- D5 The shape agreed before the interview -> three levels. `critical`: tests only for critical functions — money, access rights, data loss, the project's own non-trivial logic; no tests for calls into a ready SDK and for glue; coverage ratchet off. `standard`: a test for every behaviour change, ratchet per plan. `release`: full coverage, ratchet per task. The smallest is the default and the question says why. `/test`, before a release or by hand, first analyses the code and the existing tests, then proposes what to cover, and writes only after agreement.
- D6 Branch: `main`. Release by the standing authorization: `CHANGELOG.md` entry, commit, `stable-*` tag, ordinary `git push`; a force push is never made by the session.
- D7 The red baseline, if any, is accepted as recorded at T00 (same answer as for the previous plan).

## Assumptions
- At `critical`, "red first" stays for every test that is written and reverse control stays for tests guarding critical code: measured, red first cost 0–1.7% of active time in five of six projects and 5.9% in the sixth, reverse control at most 1.1% in all six. What `critical` removes is the test for non-critical code and the ratchet.
- The largest measured bucket, the gate set before a task mark, was addressed by the previous plan (`cc-pertask`); this plan does not touch it.
- "Critical code" is defined once, in the contract, and every other file refers to that definition: money and arithmetic on it, access rights and authorisation, deletion, migration and anything else that can lose or corrupt data, and the project's own non-trivial logic (branches, state, parsing, boundaries, retry and idempotency). Not critical: a call into a ready SDK or library, wiring, configuration, layout.
- The row is `| Test coverage level (critical / standard / release) | critical |` in the §6 coverage table of the template; a filled default, like the per-task limit row, so a completed intake leaves no `_unanswered_` cell for it.
- The ratchet is switched by where its command is written, not by code: at `critical` `/intake` does not put `python3 scripts/coverage_gate.py --run` into the gate list and `/plan` does not write it into verify lines even when an older `PROJECT.md` lists it; at `standard` it runs at `T00` and at the plan's close; at `release` it is a gate command. `scripts/coverage_gate.py` and `hooks/integrity-check.py` are not changed; lowering a floor by hand stays a recorded decision at every level.
- The level lookup for task trees lives in `format2.py` alone, so the upgrade of an existing tree is one file. `/task` detects an older validator by `cmp` with the installed template's `format2.py`; the accepted upgrade copies that file and adds an entry to the tree's `tasks/DECISIONS.md`, because `README.md` and `PROTOCOL.md` of an existing tree outrank the skill and are the owner's text. A declined upgrade leaves the tree on its own rule.
- `/plan` decides at plan time which logic tasks touch critical code; the task line carries either its test or `no test (critical level: <reason>)`. `/run-task` follows the line; when the code turns out to be critical while the task is done, it writes the test, logs the change under `## Assumptions` and does not ask.
- A value of the row outside the three is a problem for `project_check.py`; `format2.py` and a session that meet one work as at `standard` (the stricter reading of an unreadable choice), and the session says so in `## Log`.
- At `critical` `/intake` fills the five coverage cells of §6 (command, report format, floor, ratchet, areas left uncovered) with `n/a (level critical)`, so a completed intake leaves no `_unanswered_` cell and `project_check.py` passes; raising the level later replaces them with real answers.
- Every prose task keeps the tokens that existing reference checks pin in the file it edits (`cc-pertask run`, `cc-pertask record`, `cc-pertask status`, `Per-task limit for gate checks`, `no-logic`, the intake and outward-speech checks): before editing a file, `selftest.sh` is searched for the checks that name it. These edits are confirmed by the full selftest only at T13.
- No reminder or automatic `/test` at a milestone: the owner raises the level or calls `/test`.
- `claude -p` in an agent case loads the installed `~/.claude/CLAUDE.md`, so the live case runs after the live install (T14 before T15). Between the install and the live case the new contract is already in force for other sessions on this machine; a failed live case goes to `/diagnose` and a fix task, not to an uninstall.
- This plan runs under the contract as it stood at T00: every logic task here writes its test first and keeps the red output in `.claude/scratch/lean/`.
- Tag: `stable-2026-11-22-2` when the release commit is made on 2026-11-22, otherwise `stable-<date of the release commit>`.
- Before every commit of this plan the added lines of the staged diff are searched for the names of the directories next to this repository and for home paths; T16 repeats the search on the added lines and the messages of the whole outgoing range. A sibling directory whose name is a dictionary word (`/usr/share/dict/words`) or a top-level name of this repository is left out of the pattern: such a word occurs in honest text and does not identify a project. Each remaining name is searched as written and with `_` and `-` swapped.
- The numbers from the timing reports appear only with the labels project A…G; paths of the reports are not written into any tracked file.
- T01: a VERIFY item that names reverse control without the mutation and the test stays an error at every level; only the absence of the item is allowed at `critical`. A claim of a check that cannot be traced is false at any level.
- T05: the template row `Ratchet per task or per plan` is removed, the level decides it (`standard`: at `T00` and at the plan's close; `release`: with the gate checks). Four coverage cells remain for `/intake` to fill with `n/a (level critical)`, not five.
