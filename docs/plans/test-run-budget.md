# Test run budget: a per-task time limit for gate checks, no gate task for no-logic plans, one session-timing tool

## Goal
Timing of nine projects (2026-11-22) showed that writing tests costs about as much as writing product code (0.1–1.6×) while running checks costs 2–40× of it, and that the cost follows the duration of what is run before each `[x]`: a 3-second suite before 11 of 20 marks cost 8% of a plan, a 193-second local CI run about 20%. When this plan is done, the set of gate checks run before a task mark is held to a measured time limit (30 s unless the project says otherwise) by a command, not by the agent's judgment; checks that do not fit run before anything leaves the machine and when the plan closes; a plan made only of no-logic changes carries no task that runs heavy suites; and the harness has one session-timing tool that reports, for a plan, how much active time went to runs, with background runs counted as runs.

## Acceptance criteria
- [ ] AC1 With a measured gate set over the limit, `cc-pertask run` runs the cheapest commands that fit the limit and reports every other one `SKIPPED (per-plan)`, exit 0, without running it; with the set within the limit every command runs — `python3 -m unittest selftest/test_pertask.py` (`test_over_limit_skips`, `test_cheapest_first`, `test_within_limit_runs`)
- [ ] AC2 An unmeasured command runs and its duration is recorded; a failing command's exit code is passed through; a skipped command is never reported as passed — `test_unmeasured_runs`, `test_exit_code_passes`, `test_skip_is_not_pass`
- [ ] AC3 `cc-pertask status` exits non-zero while a command skipped in this plan has not run since its last skip, and 0 after `cc-pertask record` ran it — `test_status_deferred`, `test_status_clear`
- [ ] AC4 The limit is 30 s by default, is taken from the `Per-task limit` row of `docs/PROJECT.md` whatever the layout of that file, and from `--limit`; a project without `docs/PROJECT.md` works — `test_limit_default`, `test_limit_from_project`, `test_limit_flag`, `test_no_project_file`
- [ ] AC5 The contract, the template and the skills name `cc-pertask` where they say what runs before `[x]`, say that deferred checks run before a push or a deploy and at plan close, and no longer say the fast tier is copied into every verify line; `/plan` and `/task` forbid a heavy-suite task in a no-logic plan — `./selftest.sh` (`rules-pertask-*`, `rules-no-gate-task-*`)
- [ ] AC6 On synthetic transcripts `cc-sessiontime` counts a background run as a run from its call to its notification, gives an agent file outside the window zero minutes and no negative duration, ignores heredoc bodies when classifying, starts a tool interval at the end of its assistant message, does not count the idle between two legs of a resumed agent, and puts the tool wait of an edit-and-run command into runs; for every transcript items + idle = span — `python3 -m unittest selftest/test_sessiontime.py`
- [ ] AC7 `cc-sessiontime --plan <plan>` prints the share of runs in active time, run minutes per task, the unclassified share with its longest commands and one `timing:` line for `## Log`; run on a finished plan of this repository it agrees with three independent facts (items + idle = span, an agent's recorded `duration_ms`, the time between two commits) — unit tests + `.claude/scratch/test-run-budget/real.md`, facts in `## Log`
- [ ] AC8 `install.sh` installs `cc-pertask` and `cc-sessiontime` with their packages, `uninstall.sh` removes them, a trial install passes its selftest — `./selftest.sh <trial target>`
- [ ] AC9 No regression: every selftest check green at T00 is green at the finish; `./agenttest.sh --self-check` prints `agenttest self-check: ok` — `./selftest.sh; ./agenttest.sh --self-check`
- [ ] AC10 Released: `CHANGELOG.md` entry, tag `stable-2026-11-22` on the final commit, pushed — `git ls-remote --tags origin stable-2026-11-22 | grep -q .`

## Decisions
- D1 What is the limit and where does it live -> 30 seconds by default, stored in `docs/PROJECT.md` §6 and changed by one line. The set is measured; over the limit it does not run before every `[x]`, where only the tests of the touched files run. No modes, no migration.
- D2 When do the checks that do not fit run -> before anything leaves the machine (push, deploy) and when the plan closes, not before each mark.
- D3 A rule "do not wait for a background check" -> not made.
- D4 How many plans -> two. This one: the limit, no separate "checks before sending" task with heavy suites for no-logic changes (copy, legal text, styles, templates, docs, config values), the timing tool. The `lean` mode (which code gets a test, the coverage ratchet off until a release, `/test` proposes a list first) is the second plan.
- D5 The orchestrator's re-check of a worker's run (`skills/run/SKILL.md`, delegate step 3) -> untouched.
- D6 The timing tool -> part of the harness, one script instead of seven diverged copies; classification rules come from the project (the check commands of §6 plus two new rows: product code paths, test paths); background runs are runs, not idle.
- D7 A target number -> none yet. The tool prints the share of runs in active time and run minutes per task when a plan closes; `/run` writes that line into `## Log`. A report, never a gate.
- D8 Branch: `main`, a commit per task, push with the release (standing authorization: CHANGELOG, commit, `stable-*` tag, push).

## Assumptions
- The limit is enforced by a wrapper around any command (`cc-pertask`), not by a flag of `cc-fullrun`. Reason, checked 2026-11-22: of the measured projects project A's `docs/PROJECT.md` has no gate section, project B and project F declare gate checks without `### Fast tier`, project G uses the template layout with `<T00 commit>` placeholders the engine cannot run, project C has no `docs/PROJECT.md`; `fullrun/engine.py` exits 2 in four of five. A wrapper works in all of them and composes with the engine: `cc-pertask run --plan <plan> -- cc-fullrun --tier fast --out <plan dir>`.
- The per-task budget is filled cheapest-first: commands of the plan's gate set are ordered by their last measured duration, the longest prefix whose sum is within the limit runs before `[x]`, the rest are deferred. A two-second linter keeps running beside a deferred three-minute suite. This refines D1 (which speaks of the set as a whole); the set run before a mark still never exceeds the limit.
- The gate set of a plan is what `cc-pertask` has seen for that plan: `record` at T00 measures every gate command, `run` before `[x]` decides. State: `.claude/scratch/pertask/<plan path with / as _>.json`. Lost state means unmeasured, and an unmeasured command runs once and is recorded.
- The row in `docs/PROJECT.md` is `| Per-task limit for gate checks, seconds | 30 |`, read by its label wherever it stands in the file.
- "Leaves the machine" in the rules means `git push` and any deploy; the rule is prose in the contract and the skills, `cc-pertask status` is the command that proves deferred checks ran before a plan closes. `git-guard` is not changed.
- project A's task "checks before sending" (e2e, integration, `pytest tools`, twice, for a legal-text edit) came from that plan's own `## Decisions`, not from `task.txt` VERIFY or the project's `tasks/PROTOCOL.md` (both read). The fix therefore belongs in `/plan` and `/task`.
- cc-harness has no `docs/PROJECT.md`; its gate is `./selftest.sh` and `./agenttest.sh --self-check`. Tasks here verify with the unit tests of the files they touch; the whole `./selftest.sh` runs at T00, in the tasks that change `selftest.sh` itself (it is their touched file) and before the release.
- Timing tool: the window of a plan is the first to the last commit that touched the plan file unless `--from/--to` are given; time is attributed to a task by the `- [ ]` to `- [x]` flips in the git history of the plan file; transcripts are found by the working directory recorded inside their entries (T01 settles the exact fields), so sessions started in a subdirectory or a worktree of the repository are included.
- Runs are matched by runner token (`pytest`, `vitest`, `go test`, the first words of the project's gate commands), not by the full command: agents ran `timeout 300 uv run --frozen pytest … | tail`.
- Not ported from the per-project scripts: the four "mechanism" heuristics (red-first, defect planting, orchestrator repeat, gate before a mark). Each copy matched them by that project's file names and command shapes.
- Fixtures for the timing tool are synthetic; nothing from a real transcript is committed.
- `docs/tech/claude-code-transcripts@2.1.330.md`: the format is largely undocumented. An item cites the official page where one exists, otherwise the local evidence (Claude Code version and the field as observed); this is a declared deviation from "an item without a URL is not written".
- The new prose rules are checked by reference (the command is named, the retired phrase is gone), not by a live `/plan` run: no agenttest case is added, since each costs a real model run. That boundary is stated in the release entry.
- A pre-existing red check at T00 is recorded and accepted as the baseline.
- `cc-pertask`: a failed run replaces the stored duration only when it took longer (a red run usually stops early and would move a long suite into the per-task set); a passing run always replaces it. A limit row that is not a positive number (`_unanswered_`, empty, 0) means the default.
- `cc-pertask status` exits non-zero only for a skipped command that has not run since; a deferred command that ran red clears it (AC3: "0 after `cc-pertask record` ran it"), because a red accepted at T00 must not hold a plan open for ever. The red itself reaches the caller through the passed exit code and shows in `status` as `last exit N`.
- `cc-pertask` takes the project root from `git rev-parse --show-toplevel` and falls back to the current directory; `--plan` is resolved against the current directory, the command runs under `bash -c` in the current directory.
- `uninstall.sh` took its bin directory from `$HOME/bin` whatever the target, while `install.sh` uses `<target>/bin` for a target other than `~/.claude`; uninstalling a trial removed the live commands. Fixed in T04 with its own check, because AC8 ("`uninstall.sh` removes them") cannot hold while the script removes them from the wrong directory. `uninstall.sh` still leaves `<target>/fullrun/` behind when the backup has none; that is older behaviour and not this plan's.

## Out of scope
- The `lean` mode: which code gets a test, the coverage ratchet, reverse control, `/test` proposing a list (second plan).
- The orchestrator's re-check of worker runs; any rule about waiting for background checks; a target ratio or share.
- Editing `docs/PROJECT.md` of any other project, or migrating gate sections written in an older layout. Other projects receive the rule through the installed skills and the default of 30 s.
- `fullrun/engine.py` tier logic, `fast_doubled`, the census.
- The four mechanism heuristics; device, deploy, browser and record-keeping time beyond showing them as categories.
